Testing the Whole Pipeline

Edit, Commit, Push

  1. Open README.md in the VSCode editor, add a sentence, save (Ctrl+S / Cmd+S)
  2. Click the Source Control icon (branch icon, left sidebar)
  3. Hover over the changed file, click + to stage it
  4. Type a commit message (e.g. “first commit”)
  5. Click the checkmark (✓) to commit

This Is Crucial!

Committing only saves the change locally. You must also click Sync Changes (or … → Push) to actually send it to GitHub!

Verify It Worked

  • Go to your repo on github.com
  • Refresh the page
  • You should see your edited README.md with your new sentence

Git Practice

Part 1: Add and Push a File

  1. In your LIN_301 repo, create a new file called setup_notes.md, describing what you’ve done so far in setting up VSCode and Git
  2. Save, then check Source Control — notice this file is marked differently than README.md was earlier (untracked, not modified)

Part 2: Cause (and Fix) a Merge Conflict

Goal: see a conflict happen on purpose, in a safe spot, before it happens to you by accident.

  1. On github.com, open your LIN_301 repo → click into setup_notes.md → click the pencil icon to edit → add a line, then commit the change directly on GitHub
  2. Back in VSCode — without pulling first — edit setup_notes.md locally, adding a different line. Save, stage, commit.
  3. Try to push. What happens?
  4. Pull. VSCode will report a conflict — open the file and look for the conflict markers: <<<<<<<, =======, >>>>>>>
  5. Decide what the file should actually say, remove the markers and leave only the final version, then stage, commit, and push
  6. Refresh github.com to confirm your resolved version made it up

Make VSCode Yours

Activity: Customize Your Setup

  • Open Settings: gear icon (bottom-left) → Settings, or Ctrl+, / Cmd+,
  • Try at least two of the following:
    • Color Theme — Ctrl+K Ctrl+T / Cmd+K Cmd+T, browse and pick one

Why Good File Organization Matters

A Preview of What’s Coming

Principles of Good File Organization

Naming Conventions: No Spaces

  • my data.csv → the command line and Python may choke on this
  • my_data.csv or my-data.csv → safe everywhere
  • We’ll see exactly why next class, but get in the habit now

Naming Conventions: Case & Clarity

  • Prefer lowercase — avoids Mac vs. Windows vs. Linux case-sensitivity headaches
  • Be descriptive, not generic:
    • data1.csv → jfk_speech_tokens.csv
    • hw.qmd → hw3_beginning_python.qmd
  • Use ISO dates (YYYY-MM-DD) if a filename needs one — they sort correctly

Version Numbers vs. Git

  • Old habit: paper_v1.docx, paper_v2.docx, paper_FINAL.docx, paper_FINAL_v2.docx
  • New habit: one file, paper.qmd — and let Git track every version for you
  • This is exactly what you set up today. You don’t need “v2” in a filename ever again.

Folder Hierarchy

  • Don’t dump every file into one giant folder
  • Group by purpose:
LIN_301/
├── homework/
├── classwork/
├── data/
└── README.md
  • Don’t go too deep either — 2–3 levels is usually plenty. If you need a map to find a file, it’s too deep.

README Files

  • Every good project folder has a README.md at the top
  • It answers: what is this project? how is it organized? how do I use it?
  • You already have one — set up in your Git repo!

Wrap-Up

Big Takeaways

  • Good naming and structure isn’t pedantic — it prevents real bugs later in the semester
